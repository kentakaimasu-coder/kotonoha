# Phase 0: 要件定義書・技術仕様書の整合性検証

状態: レビュー待ち / 最終更新: 2026-11-02 / 上位文書: [01_requirements.md](../requirements/01_requirements.md), [02_technical_spec.md](../requirements/02_technical_spec.md)

対象: 要件定義書 1.0-draft、技術仕様書 1.0-draft(いずれも 2026-11-03 付)、CLAUDE.md(実装指示)。
アップロードされた .docx と .md の内容は同一であることを `pandoc` の平文比較で確認した。

分類:
- **C (矛盾)**: 文書間・文書内で両立しない記述
- **U (未確定)**: 実装に必要だが決まっていない事項
- **I (実装課題)**: 決まっているが、そのままでは実装・検証できない事項

各項目の「扱い」は次のいずれか:
- **ADR提案**: 推奨案を `docs/adr/` に「提案」状態で記録し、**仮実装した**(承認されれば確定、却下なら修正)
- **ブロッカー**: 推奨案を記録したが、承認まで実装しない
- **検出のみ**: コンパイラが診断として検出する(仕様側の修正が必要)

> 本書の「推奨案」はいずれも **未承認** です。承認者の確認なしに確定仕様として扱わないでください。

## 1. 矛盾(C)

| ID | 内容 | 根拠 | 扱い |
|---|---|---|---|
| C-01 | §2 のサンプルが §3.2 の規則で解析できない。`注文IDを返す` は空白がないため、識別子規則(語=文字の最長連続)では 1 語になり、`返す` 文にならない。一方 `商品をIDで取得` は 1 語の識別子として使われている。「助詞で自動分割する」と「最長一致」は両立しない | 技術仕様 §2, §3.2 | ADR-0101 提案: 助詞は自動分割しない。予約語 `を返す` `を確認` は空白で区切る。サンプルは `注文ID を返す` に修正が必要。コンパイラは SYN001 と修正ヒントを出す(テスト `spec_sample_fails_only_on_unspaced_return`) |
| C-02 | §2 のサンプルは `注文ID` `注文失敗` `注文`(データ)、`商品をIDで取得` `注文を登録`(操作)を定義せずに使っている。§2 の注記は「明示的なアダプタ定義が必要」と書くが、その構文が無い。FR-004「未定義参照をビルド時に拒否」に従うとサンプル自体がビルドできない | 技術仕様 §2 注, FR-004 | ADR-0104 提案(`アダプタ` 宣言)、ADR-0102 提案(`型` `列挙`)。サンプルは REF001 を出す(テスト `spec_sample_undefined_names_are_ref001`)。補完版は `examples/shop` |
| C-03 | VAG の例の `screen.products` は `effects:["data.read"]` を持つが、§9 は「画面の権限表示だけでは保護としない」。一方 `action.order` の capabilities は `["注文.create","商品.update"]` で、処理は `商品をIDで取得` を呼ぶ(=読取)。更新が読取を含むのかが不明 | 技術仕様 §6, §9, SEC-01 | ADR-0105 提案: **更新は読取を含まない**(デフォルト拒否を優先)。サンプルの `必要 = [注文.作成, 商品.更新]` は SEC002 になる(テスト `missing_capability_is_sec002`)。代替案「更新⊇読取」も ADR に記載 |
| C-04 | ロックの最低フィールドは単数の `target` だが、CLI は `--target web|backend|ios|android`、要件は「単一の意味モデルから複数ターゲット」。ターゲットごとにロックを分けるのか、1 つのロックで複数を固定するのか不明 | 技術仕様 §13, §14, 要件 §1 | ADR-0109 提案: `targets` 配列で 1 ロックにまとめる |
| C-05 | §14 の終了コードに「未承認」(APP001)と「参照エラー」(REF001)の割当がない | 技術仕様 §14, §15 | ADR-0103 提案: APP001→3(曖昧)、REF001→2(構文/型) |
| C-06 | §8 の SQL 参考出力は `status = 'confirmed'` のように値を直書きしているが、SEC-04 は「バインド変数のみ」 | 技術仕様 §8, SEC-04 | 生成 SQL はすべてバインド変数(状態値・期間・件数)。テスト `sec04_no_values_are_inlined_into_sql` |
| C-07 | §7「`@柔軟(自動)` は承認済みの知識と別名だけを使用」と FR-005「承認済み意味を一意に解決」の関係が曖昧。別名解決は `@厳密` でも使えるのか、`@柔軟(自動)` 固有なのか | 技術仕様 §7, FR-005 | ADR-0112 提案: 知識名・別名はすべてのモードで使う。`@柔軟(確認)` は意図 ID 単位の承認、`@柔軟(自動)` は同一文(文ハッシュ一致)への承認の再利用、`@厳密` は承認を適用しない |
| C-08 | §3.3 EBNF は `action` の本体に `intent_line` を許すが、動作本体の意図文型は §5 の有限集合に定義が無い | 技術仕様 §3.3, §5 | MVP は動作本体の意図行を常に AMB001 とする(推測で解釈しない) |

## 3. 実装上の課題(I)

| ID | 内容 | 扱い |
|---|---|---|
| I-01 | 意図層の文は形態素解析なしでは助詞境界が取れない。日本語文の一般解析は非目標(要件 §1.2) | 文型は「接尾辞・接頭辞の固定文字列 + 宣言名の完全一致」に限定(docs/spec/intent_patterns.md)。形態素解析器に依存しないので決定的 |
| I-02 | 「AI 出力を直接実行しない」を構造的に保証する方法 | 承認対象は「既知の文型の正規文への書き換え」だけ。正規文も同じ照合器を通る(承認記録に任意コードを入れても APP001)。テスト `approval_must_be_a_known_pattern` |
| I-03 | `validated` の付与条件(承認・型・効果・権限・参照整合性) | 全診断にエラーが無い場合のみ `validated`、それ以外は `draft`。`koto graph` は既定で draft を出力しない |
| I-04 | 「同じ固定入力から同じ正規化 IR」(FR-020) | VAG はソース・承認記録のみに依存(時刻・環境・乱数・HashMap の順序に依存しない。BTreeMap とソート済み配列のみ使用)。テスト TC-009 |
| I-05 | コメント保持付きの整形 | Surface AST はコメントを持たない。`koto fmt` はテキスト正規化のみ(ADR-0107)。AST プリンタはラウンドトリップ検証専用 |
| I-06 | ノード ID の安定性(§6「宣言の安定ID」) | 宣言は名前、意図は `所有者#文ハッシュ12桁`。行の並べ替えで ID は変わらない(テスト `intent_ids_are_stable_against_reordering`)。同一画面内の同一文は `~2` 付き |
| I-07 | JSON の正規化方式 | serde_json の BTreeMap 順(UTF-8 バイト順)。RFC 8785 JCS の UTF-16 順とは非 BMP 文字で異なりうる。数値は整数のみ |
| I-08 | 推奨モジュール構成(§17)の `approval` と `lock` | 1 クレート(`lock`)に統合し、`driver` を追加(ADR-0114) |
