# ADR-0130 専門用語を覚えずに書ける動作と、日本語で確かめる「確かめる」
状態: 提案(実装) / 日付: 2026-11-09 / 関連: 第 3 回ペルソナ評価(docs/evaluation/persona/results_round3.md §2)、ADR-0102、ADR-0104、ADR-0105

## 背景
第 3 回ペルソナ評価で主観評価が上がらない理由の上位は「アダプタ・厳密・取引の意味が分からないまま写した」(60 人中 50 人)と
「動作確認に curl・トークン・URL エンコードが要る」(55 人)だった。

## 決定(提案)
1. **`厳密:` の見出しを省略できる**: 動作の下(`必要`・`効果` 以外の行)を、そのまま厳密層の処理として読む。
   以前は「動作本体の意図行」として常に AMB001 になっていた(文型を定義していないため)ので、意味の衝突はない。`厳密:` も引き続き書ける
2. **データを変える動作は、本体全体が自動で 1 つの取引**: 権限に 作成・更新・削除 を含む動作は、生成コードで本体全体を取引にする。
   途中で失敗したら、それまでの変更はすべて元に戻る(同時実行でも数が合う)。`取引:` は書かなくてよく、書いた場合はその取引に含まれる。
   型検査の「エンティティの更新は `取引:` の中だけ」(TYP002)は廃止。動作から動作を呼んだときの入れ子の取引は、外側の取引の一部として実行する
3. **組込みのデータ操作**: `アダプタ` を宣言しなくても、動作の中で `{データ}を取得(ID)`(`をIDで取得` も可)・
   `{データ}を登録(ID を除く項目を宣言順に)`・`{データ}の一覧()` を呼べる。実際に呼ばれたものだけを用意する(VAG・生成物は従来と同じ形)。
   同じ名前のアダプタ・動作を宣言していればそちらを使う。引数の数が違うときは、引数の順と型をヒントに出す
4. **`必要 = [...]` を省略できる**: 省略したときは、処理が触れるデータ(取得・登録・更新・削除・呼んだ動作)から必要な権限を決める。
   既定ですべて禁止(権限はトークン・役割で与える)・実行時の権限検査は変わらない。書いた場合は、使わない権限も含めて宣言どおり要求する
5. **確かめる**: トップレベルに `確かめる 名前:` と日本語の手順を書くと、`koto test` と `koto dev`(起動前)が、
   初期データ(seed.json)だけの新しいデータベースで試し、✓ / ✗ と実際の値を日本語で表示する(curl・トークン不要)。
   - `花子(利用者)が 予約する(s1, 2) → 成功` / `→ 失敗("満席")` / `→ ログインが必要` / `→ 権限がない` / `→ 重複` / `→ 見つからない`
     (人は 名前(役割)・名前(役割を省くと一般の利用者)・`ログインしていない人`)
   - `花子から 予約が 1件見える`(一覧 API で、その人に見える件数)
   - `枠(s2)の予約数は 2`(データベースの値)
   - 動作・データ・項目・役割の名前、引数の数と値の型は `koto check` で検査する。アプリの意味(VAG・ロック)には入らない
6. ひな形 4 つを新しい書き方(アダプタ・厳密・取引・必要 なし、確かめる付き)に書き換えた。`koto patterns` に、自分のデータ名で
   動作の中の文と確かめるの文を出す

## 採らなかった案
- 名前付き引数(`予約を登録(枠ID: …, 人数: …)`): 構文木の変更が大きいため見送り。値は項目の順に並べ、違えば引数の順と型をヒントに出す
- `取引:` を廃止: 既存のソースのために残す(意味は自動の取引の一部)
