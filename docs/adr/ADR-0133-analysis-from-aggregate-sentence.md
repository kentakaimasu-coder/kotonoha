# ADR-0133 分析を集計の文で書く(SQL なし)
状態: 提案(実装) / 日付: 2026-11-09 / 関連: 第 4 回ペルソナ評価(results_round4.md §2)、ADR-0125(分析)、ADR-0128(日本語の集計)

## 背景
第 4 回ペルソナ評価で、60 人中 59 人が「会場別の集計に SQL が要る」をつまずきに挙げた(非エンジニアは「ここだけ普通のプログラミングに戻った」)。
日本語の集計の文(ADR-0128)は画面に表を出せるが、API の名前(`/api/aggregates/見出し`)と列名(`件数`・`予約数の合計`)は固定で、
業務で決まっている API の名前・列名(`/api/analyses/会場別の予約状況`、`イベント数`・`定員`)には合わせられなかった。

## 決定(提案)
`分析` に `SQL = "…"` の代わりに **`集計 = "…"`** を書ける。
```kotonoha
分析 会場別の予約状況() -> 一覧<記録{会場: 文字列, イベント数: 整数, 予約数: 整数, 定員: 整数}>:
    集計 = "イベントの予約数と定員を会場ごとに合計"
```
- 文は画面の集計と同じ文型(`…ごとに集計` / `…の F と F を…ごとに合計` / `…のうち 条件 のもの…`)。コンパイラが SELECT 文を作り、
  **その SELECT は手書きの SQL と同じ検査(SELECT 1 文・宣言した表だけ)を通す**
- 結果の列(単位・件数・各合計)を、戻り値の記録の列に**順に**当てはめる。列の数・型が合わなければ、期待する列を示すエラー
- `対象` は省略できる(文のデータ)。公開範囲・PostgreSQL の数値の扱いは SQL の分析と同じ
- 未対応(エラーで案内): 日ごと・月ごと、`今日` / `本人` などの絞り込み、引数のある分析。これらは SQL で書く

## 確認
- 第 4 回の参加者の A を `集計 = "…"` に書き換え、評価の採点(F14 会場別の集計が一覧と一致)に合格
- e2e(SQLite・PostgreSQL): 列名が記録どおり、絞り込み(取下げを除く)、本人限定データは全件閲覧の許可が要る
