# ADR-0128 一覧の並べ替え・絞り込みと、日本語の集計
状態: 提案(実装) / 日付: 2026-11-08 / 関連: ペルソナ評価 第 2 回の残要望(docs/evaluation/persona/results_round2.md §4)、ADR-0111、ADR-0118、ADR-0125

## 背景
第 2 回のペルソナ評価で「今日の分だけ・納期順・未完了だけを出したい」「集計に SQL が要る」が多かった。

## 決定(提案)
### 1. 一覧の並べ替え・絞り込み(P-LIST の拡張)
- 文型は docs/spec/intent_patterns.md の P-LIST(並べ替え)・P-LIST(絞り込み)。照合は字面で行い、フィールド名・列挙値・値の型をコンパイル時に検査する
  (知らないフィールドは REF001、型に合わない値は TYP001、知らないデータは AMB001)
- 共通 API 契約の一覧 API に固定のクエリを付けて表す: `?eq.F=値&ne.F=値&today.F=1&me.F=1&order=F&desc=1`。
  Web / iOS / Android は画面ごとに決まったクエリで同じ一覧 API を呼ぶだけで、業務ロジックはクライアントに持たない(不変ルール 4)
- backend はフィールド名を表の定義と照合し(SQL に値を埋め込まず、識別子も定義にあるものだけ引用して使う)、値を型で検証する。
  本人の行だけの条件(C-OWNER)は常に併せて適用するため、絞り込みで他人の行が見えることはない
- `今日` はアプリの時刻帯(環境変数 `KOTONOHA_APP_TZ`、既定 Asia/Tokyo)の暦日。`でない` は値が空の行も含める
- VAG の一覧ノードの detail に `order` / `filters` を記録する(並べ替え・絞り込みが無い一覧の VAG は従来と同じ)

### 2. 日本語の集計(P-AGGREGATE)
- 文型は docs/spec/intent_patterns.md の P-AGGREGATE。結果は「単位・件数・各合計」の表(列名は `品名` / `注文日時の日` / `件数` / `金額の合計`)
- 集計ごとに固定の API(`GET /api/aggregates/{見出し}`)を作り、応答の型を共通 API 契約に記録する。同じ内容の集計は 1 つにまとめる。
  単位・合計するフィールド・絞り込みはコンパイル時に決まり、クライアントからは変えられない
- 権限は対象データの読取と同じ。本人限定のデータは本人の行だけを数える(`全件閲覧.データ` を持つ人は全員分)
- backend は絞り込み後の行を読み、単位ごとに数える(日時の日・月をアプリの時刻帯で区切るため、SQL 方言に依存しないため)。
  行数が多いデータ(数十万行〜)では遅くなる。大量データの集計は従来どおり `分析`(SQL)を使う(K-31)

## 採らなかった案
- 一覧 API に任意の並べ替え・集計の指定を受け付ける: クライアントから何でも指定できると API 契約が曖昧になるため、文に書いたものだけを固定のクエリ・固定の API にした
  (一覧の並べ替え・絞り込みのクエリは定義済みのフィールドに限って受け付ける)
