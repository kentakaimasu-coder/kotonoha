# ADR-0142 公開に外部のログインのサービスを要さない「アプリの中のログイン」
状態: 決定(選択肢 2) / 日付: 2026-11-17、決定 2026-11-18 / 関連: ADR-0139(公開の点検)、ADR-0140、[第 14〜16 回評価](../evaluation/persona/)

## 背景
第 14〜16 回の評価で、3 倍に届かない理由に「公開には外部のサービス(ログインの仕組み・置き場所)との契約が要り、一人ではできない」が毎回挙がる
(第 15 回 2 人、第 16 回 1 人。3 倍以上の人も差し引いた理由に挙げることが多い)。
いまの生成アプリは、本番のログインを OIDC(外部の認証基盤)に任せている。開発用ログイン(名前だけで入る)は本番では使えない。

## 選択肢
1. いまのまま(本番は OIDC のみ)。公開の手引きに、よく使う認証基盤の設定の手順を足す
2. 「アプリの中のログイン」を足す: 利用者をアプリの中に登録し(招待のリンクかメールアドレスとパスワード)、役割を管理者が画面で付ける。
   パスワードは強いハッシュで保存し、試行回数の制限・セッションの期限・CSRF 対策は今のものを使う。OIDC と選べるようにする
3. 2 を、メールで届くリンクだけでログインする形(パスワードを持たない)にする。メールを送る仕組みが要る

## 決定
利用者(作り手)の承認(2026-11-18「やって どんどん追加機能の実装や修正してね」、提案中の ADR-0141・0142 を決めてほしいと伝えた返答)により、選択肢 2 にする。

### 仕組み(runtime/web/local_login.ts・runtime/web/server.ts)
- 有効にする: web の環境変数 `KOTONOHA_LOCAL_LOGIN=1`(`koto publish` の `.env` は最初からこれ)。署名には backend と同じ `KOTONOHA_JWT_SECRET` を使う(本番は 64 文字以上でないと起動しない)
- 利用者の一覧: JSON のファイル(`KOTONOHA_USERS_FILE`、既定 `./data/users.json`、0600)。書くときは別名で書いて置き換える
- パスワード: scrypt(N=2^15, r=8, p=1, 塩 16 バイト)。比較は時間一定。10 文字以上・ログイン名と同じ不可・単純なもの不可。知らないログイン名でも同じだけ計算する
- 失敗が続いたら止める: 同じログイン名で 5 回 → 15 分、同じ接続元で 30 回 → 15 分。止めている間は正しいパスワードでも入れない
- ログインの印: HS256 の JWT(sub・名前・役割・権限・版・期限 12 時間)を HttpOnly・SameSite=Strict の Cookie に入れる。
  権限は役割の権限と、役割に関わらない操作の権限(ADR-0140。生成物の `webApp.general`)。
  web は毎回「利用者がまだいるか・版が今のものか」を確かめ、合わなければログインしていない扱いにする(役割の変更・削除・パスワードの変更で古い印は使えなくなる)
- 最初の管理者: 利用者が 0 人のとき、起動の記録に一度だけ使える URL(`/setup?t=…`。`KOTONOHA_SETUP_TOKEN` で決めてもよい)を出す。最初の管理者はすべての役割を持つ
- ほかの人: 管理者が「利用者の管理」(`/users`)で招待のリンク(7 日・1 回)を作り、役割を付ける。再設定のリンク(24 時間・1 回)・役割の変更・削除もここ。リンクの秘密は SHA-256 だけを保存する
- 自分のパスワードの変更: `/account`
- フォームの POST は別のサイトからは受け付けない(Origin・Sec-Fetch-Site。ログイン CSRF 対策)
- OIDC も使える(`.env` に `KOTONOHA_OIDC_…` を入れると、start.sh はアプリの中のログインの代わりにそちらを使う)
- テスト: tests/e2e/local_login.test.ts(最初の管理者・招待・役割・失敗が続いたときの停止・印の取り消し・ログイン CSRF・本番の設定)

### 残るリスク(利用者に伝える)
- 認証を自前で持つため、利用者の一覧のファイル(`data/users.json`)の保管とバックアップは作り手の責任になる
- メールでの本人確認・二要素認証は無い(必要なら OIDC を使う)
- 失敗の回数は web のプロセスの中だけに持つ(再起動で消える。複数台で動かすときは OIDC を推奨)
- 役割を書いていないアプリでは、登録した人はみな全部の操作ができる(ADR-0140 と同じ)。登録できるのは招待した人だけなので、招待する相手で決める

## 推奨案(提案時)
2 を推奨する。小さな店・教室・サークルの規模なら、外部の契約無しに公開まで進められる。
ただし認証を自前で持つことになり、セキュリティの責任が増える(パスワードの保管・再設定・乗っ取り対策)。
要件(SEC 系)とテスト(TC)の追加が要るので、利用者(作り手)の承認が要る。決まるまでは 1 のまま
