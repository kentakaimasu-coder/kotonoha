# ADR-0132 役割で名指しした動作は、その役割だけが実行できる / 状態の順番の確かめ方
状態: 提案(実装) / 日付: 2026-11-09 / 関連: 第 4 回ペルソナ評価(docs/evaluation/persona/results_round4.md §3)、ADR-0118、ADR-0126、ADR-0129、ADR-0130

## 背景
- ADR-0130 で、動作に必要な権限は処理が触れるデータから決まるようになった。そのため「店長だけの受付を締める」と「スタッフの希望を出す」が
  同じ `シフト枠.更新` で動き、**スタッフも締切を実行できた**(E11・E21)。エラーも警告も出ず、`koto dev` の公開範囲の一覧を読んで初めて気づいた。
  既定で禁止(権限が無ければ拒否)は守られているが、**役割の意図より広く許していることに気づけない**
- 状態の順番(ADR-0129)で、承認済みの物をもう一度「承認済」にすると成功してしまう(E24)。値が変わらないので順番の検査を通らなかった
- 状態の順番に合わない操作(409)を「確かめる」で書けず、`→ 重複` で代用していた(Q03・E28 など)
- 動作の名前を組込みのデータ操作と同じ `作業を登録` にすると、処理の中の `作業を登録(…)` がその動作自身の呼び出しになり、
  「引数の数が違う」という的外れなエラーになった(E18・E28)

## 決定(提案)
1. **役割の権限に `動作.動作名` を書いた動作は、書いた役割(と全権限の人)だけが実行できる**。
   同じデータの権限を持つだけの役割には許さない(API の必要権限が `動作.動作名` だけになる)。どの役割も名指ししていない動作は従来どおり
2. `koto safety` と `koto dev` に **「役割ごとに実行できる動作」** を出す(意図しない役割が実行できないかを一目で見る)
3. 状態の順番を持つ項目に**今と同じ値を入れたら 409**(`状況は既に「承認済」です`)。取下げなど「いつでも」の値も同じ
4. 「確かめる」の結果に **`→ 順番が違う`**(`状態が違う` も可)を加える。`→ 重複` は重複不可の 409 だけに一致する(以前はどの 409 にも一致した)
5. 動作の名前が組込みのデータ操作(`{データ}を登録` / `を取得` / `をIDで取得` / `の一覧`)と同じで、処理の中で呼ばれているときは、
   名前の衝突だと説明するエラーにする(TYP001。別の名前の例を示す)
6. 役割に「管理者」があるとき、開発用ログインの組込みの全権限ボタンは「すべての権限で入る」と表示する(同じ名前のボタンが 2 つ並ばない)

## 影響
- 1 は既存のアプリで、役割に `動作.X` を書いていて、かつ別の役割がデータの権限で X を実行していた場合に挙動が変わる(実行できなくなる)。
  名指しは「その役割にこの操作を許す」意図で書かれるので、狭める方向の変更として受け入れる
- 4 の `→ 重複` は、状態の順番の 409 を `重複` と書いていた「確かめる」が ✗ になる。`→ 順番が違う` に書き換える

## 未決
- 名指しの無い動作で、意図より広く許している可能性を検査で警告する方法(役割が 2 つ以上あり、ある書き込みの動作を全役割が実行できるときなど)
