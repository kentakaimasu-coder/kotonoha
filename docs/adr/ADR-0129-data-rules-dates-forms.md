# ADR-0129 重複不可・状態の順番・日付の計算・応答の時刻帯・フォームの改善
状態: 提案(実装) / 日付: 2026-11-08 / 関連: ペルソナ評価 第 2 回の残要望(docs/evaluation/persona/results_round2.md §4)、ADR-0106、ADR-0115、ADR-0118

## 背景
第 2 回のペルソナ評価で多かった残要望: 二重登録の防止、状態の順番(受付→製作中→出荷済)の強制、日付の計算(期限・延滞)、
API の日時が UTC で返る、他の人のデータの 404 が分かりにくい、フォームのボタン文言・他のデータから選ぶ入力・複数行の入力。

## 決定(提案)
1. **重複不可(約束 C-UNIQUE)**: `{データ}は{F}と{F}の組で重複不可` / `{データ}は{F}が重複不可`。
   - backend は一意索引(名前は表とフィールドのハッシュ `uq_…`)を移行時にそろえる(宣言から消えた索引は削除)。既存データに重複があれば起動を止めて日本語で案内
   - 違反は 409 `duplicate`「既に登録されています(日報: 日付と記入者が同じものがあります)」。同時に送っても DB の一意制約で 1 件だけになる
   - 選択<…> のフィールドは使えない(空どうしは重複とみなされないため)。ID は書かない
2. **状態の順番(約束 C-SEQUENCE)**: `{データ}の{F}は 値 → 値 → 値 の順`(`の順に進む` も可)。F は列挙で、すべての値を並べる。
   - 作るときは最初の値だけ、変えるときは「同じ値」か「次の値」だけ。違反は 409 `invalid_transition`「状態は「下書き」の次は「提出済み」です(「下書き」→…の順)」
   - どの値からでも進める値(取消など)は今は書けない(将来の拡張)
3. **日付の計算(組込み関数)**: `今日()`(日付。アプリの時刻帯)、`日後(日時|日付, N)`、`日前(…, N)`、`日数差(a, b)`(b − a の暦日数)。
   `今日()` は `現在日時()` と同じく関数(副作用なし)では使えない
4. **応答の時刻帯**: API が返す日時を、アプリの時刻帯(`KOTONOHA_APP_TZ`、既定 Asia/Tokyo)のずれ付き ISO 8601(`…+09:00`)にする。
   時刻そのものは同じ(Z 表記と同じ瞬間)。入力は従来どおりずれ付きなら何でも受け付ける。Android の日時の解析をずれ付きに対応
5. **他の人のデータの 404**: 本人限定のデータでは、存在を知らせないため 404 のまま、文言を「見つかりません(無いか、ほかの人のものです)」にする
6. **フォーム**: `{動作}のフォームを「申し込む」ボタンで表示` で送信ボタンの文言を変える(Web / iOS / Android)。
   Web では、引数「データ名ID」をそのデータの一覧から名前で選ぶ欄にし(一覧を読めないときは ID の入力欄)、
   名前が「内容・備考・メモ・詳細・本文・説明・感想・コメント・相談・要望・理由」で終わる文字列は複数行の入力欄にする

7. **引数のある分析を画面に出す**: `{分析}を表示` は引数のある分析にも使える。画面に条件の入力欄(型に合わせた入力: 日時・日付・数・文字)と
   「表示」ボタンが出て、押すと結果の表を出す(Web / iOS / Android)
8. **入力のヒント**: Web のフォームの数・金額・メール・URL の欄に例(「例: 1,000(円)」など)を出す

## 検証
tests/e2e/requests.test.ts(SQLite と PostgreSQL)、tests/e2e/izakaya_app.test.ts(フォーム)、crates/intent・crates/types の単体テスト。
iOS / Android のフォームの選択欄・複数行入力・入力のヒントは未対応(ID の入力欄・1 行の入力欄のまま)。引数のある分析の画面は tests/e2e/extensions.test.ts(Web)と、モバイルは構文検査・CI のビルドで確認。
