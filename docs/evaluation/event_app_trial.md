# 実アプリ試作による評価: イベント受付(examples/event)

状態: 評価途中(**使いやすさ 300% 以上の合格判定は未実施**) / 最終更新: 2026-11-07 / 上位文書: 追補要件 NR-01・NR-05〜08

## 1. 何を作ったか
勉強会・セミナーの受付アプリ。イベント一覧 → 詳細 → 予約(1名 / 2名)→ 満席の判定 → 自分の予約、主催者のイベント登録フォーム、会場別の集計(SQL)、予約ボタン文言の A/B 実験。
Web(PC・スマホ)・backend・iOS・Android を 1 つのソースから生成。

## 2. 依頼者の合格基準と、この文書で言えること
依頼者の基準: **「通常より使いやすいという評価が今までの 300% 以上」でなければ合格としない。**

- これは「人の評価」を求める基準であり、作り手(AI)自身の評価や行数の比較では満たせない。
- したがって **現時点で合格とは判定しない**。下記 §3 は判断材料(代理指標)であり、§5 の利用者評価が合否を決める。

| 指標 | KOTONOHA | 従来の書き方で手で書く量(生成物のアプリ固有部分で近似) | 比 |
|---|---|---|---|

| 4 ターゲット(+ iOS 156 + Android 185) | 69 行 | 728 行 | 10.6 倍 |
| 共通処理(認証・認可・CSRF・入力検証・取引・ログ等) | 書かない | ランタイム 1,948 行相当(従来はフレームワーク + 自前実装) | — |
| 初回の検査 | 書いたまま `koto check` に合格 | — | — |

注意(この比較の限界):
- 生成コードは人が書くコードより冗長な場合も簡潔な場合もある。行数比は「書く量」の目安であり、使いやすさそのものではない。
- 比較対象を実際に別の技術(例: Next.js + Prisma)で人が書いて測ったものではない。

自動で入る安全性(手で書かなくてよいもの): 認証(JWT/JWKS)、権限のデフォルト拒否、本人の行だけの表示(行レベル認可)、取引と同時予約の整合(最後の 1 席を 4 人が同時に押しても 1 人だけ成功することを確認)、入力検証、CSRF 対策、CSP 等のセキュリティヘッダ、レート制限、監査ログ、アクセシビリティ(axe-core で WCAG 2.2 A/AA 違反ゼロ: PC・スマホ)。

## 4. 実際に使って見つかった問題と対処
| # | 問題(利用者から見て) | 対処 |

| 1 | 予約後のメッセージに内部 ID(UUID)が出る | 修正: 「完了しました」だけにする(K-13 改訂) |
| 2 | 日時に秒まで出る(2026/12/5 19:00:00) | 修正: 「2026年12月5日(土) 19:00」 |
| 3 | ログイン後もヘッダーが「ログイン」のまま | 修正: 「ログイン中」と表示 |
| 4 | スマホでヘッダーの並びが崩れる | 修正: 画面幅 600px 以下で段組みを変更 |
| 5 | **日時入力をブラウザの時刻帯で解釈し、表示(日本時間)とずれる**(13:00 と入れると 22:00 になりうる) | 修正: 入力もアプリの時刻帯で解釈し、項目名に「(日本時間)」を表示 |

## 5. 合否を決める利用者評価(提案)
- 方式: 同じ要件(本書 §1)を、日本人の開発者が (A) KOTONOHA と (B) 普段の技術で作る。順序は半数ずつ入れ替える
- 測るもの: 完成までの時間、作業中の誤りの数、SUS(System Usability Scale)の点数、セキュリティ項目の抜け
- 合格基準の案: 「完成までの時間が B の 1/3 以下」かつ「SUS が B より高い」(= 300% 以上の効率)。人数は 5 人以上
- 必要なもの: 協力者(依頼者側で手配)。AI だけでは実施できない
