# ペルソナ評価の結果(第 1 回)

状態: 完了(**AI が演じるペルソナによるシミュレーション**。実在の利用者評価ではない) / 実施: 2026-11-07
課題: [task.md](task.md) / ペルソナ: [personas.md](personas.md) / 採点: `tools/eval/probe.mjs`(19 項目)・`tools/eval/grade.sh` / 生データ: [reports/](reports/)

## 1. 方法
- 5 人のペルソナ(AI が演じる)が、同じ課題を **A: KOTONOHA** と **B: 普段の技術**(Flask / Express+TS / FastAPI / Express)で作った。順序は P2・P4 が B→A、他は A→B
- 品質: 出来上がったアプリを採点者が起動し、同じ 19 項目(機能 14・画面表示 1・セキュリティ 4)で自動採点
- 記述量: 手で書いたファイルの行数(空行・コメント・生成物・依存を除く)
- 主観: SUS(System Usability Scale、0〜100)をペルソナが回答

## 2. 結果
| ペルソナ | 記述量 A | 記述量 B | B/A | 品質 A | 品質 B | B の失点 | SUS A | SUS B |
|---|---|---|---|---|---|---|---|---|
| P1 社内 SE | 89 | 335 | 3.8 倍 | 19/19 | 17/19 | セキュリティヘッダ・技術の痕跡 | 65.0 | 52.5 |
| P2 Web エンジニア | 90 | 623 | 6.9 倍 | 19/19 | 19/19 | — | 67.5 | 77.5 |
| P3 データアナリスト | 77 | 397 | 5.2 倍 | 19/19 | 17/19 | セキュリティヘッダ・技術の痕跡 | 65.0 | 70.0 |
| P4 企画職 | 77 | 284 | 3.7 倍 | 19/19 | 16/19 | 日本の表記・ヘッダ・痕跡 | 65.0 | 32.5 |
| P5 新卒 | 76 | 303 | 4.0 倍 | 19/19 | 16/19 | 日本の表記・ヘッダ・痕跡 | 65.0 | 55.0 |
| **平均** | **82** | **388** | **4.7 倍** | **19.0** | **17.0** | | **65.5** | **57.5** |

作業の手数(ペルソナの自己申告): A 平均 14.6、B 平均 7.8。**A の方が手数が多かった**(下記 §4 のつまずきが原因)。
ただし B の手数の少なさは「AI が数百行を一度に書ける」ことによる面が大きく、人の作業時間とは対応しない。

## 3. 300% 基準に対する判定
| 観点 | 結果 | 300% 以上か |
|---|---|---|
| 書く量(B/A) | 4.7 倍(全員 3.7 倍以上) | **満たす** |
| 品質(採点 19 項目) | A は全員満点、B は 5 人中 4 人が失点(主にセキュリティ) | 「同等以上」は満たす(比率の指標ではない) |
| 使いやすさの主観(SUS) | A 65.5 / B 57.5(+14%)。Web エンジニアと分析者は B を高く評価 | **満たさない** |
| 完成までの手数 | A の方が多い(14.6 対 7.8) | **満たさない** |

**結論: 不合格(現時点)。** 書く量と品質では明確に優れるが、「使いやすい」という評価は 300% に遠い。
なお SUS は 0〜100 の尺度で、B の平均 57.5 の 3 倍は上限を超えるため、「SUS が 300%」という基準は成立しない。主観評価の合格基準は別に定める必要がある(案: SUS 80 以上 かつ 全ペルソナで B 以上)。

## 4. つまずき(A: KOTONOHA)と対処
| つまずき | 人数 | 対処(第 1 回の後) |
|---|---|---|
| 権限がソースでは日本語(`予約.作成`)、トークンでは英語(`予約.create`) | 5 | **修正**: トークンに日本語の動詞を書いても通る |
| backend と web が別ポートの 2 つのサーバー。API を 1 つのポートで使えない | 5 | **修正**: web のポートで Bearer の API 呼出を受け付ける(Cookie ログインの状態変更だけ X-CSRF を要求) |
| 初期データの入れ方がチュートリアルに無い。2 回入れると重複エラー | 4 | **修正**: チュートリアルに追記、同じ ID は飛ばす |
| 画面の URL(`/s/画面名`)が分からず 404 | 3 | **修正**: 404 ページに URL の形と入口の画面を表示、チュートリアルに追記 |
| `npm run token -- --help` が英語のエラーで落ちる | 2 | **修正**: 日本語の使い方を表示 |
| ログイン・ログアウトの POST に CSRF 対策が無い(P2 の指摘) | 1 | **修正**(セキュリティ): 他サイトからの POST を拒否 |
| 日時が API では UTC(`…Z`)で返る | 4 | 仕様(ADR-0117)。チュートリアルに明記 |
| 例をまねるしか書き方が分からない(どの文が通るのか) | 3 | 未対応: 文型の一覧と補完(LSP、FR-017) |
| 「自分の予約」にイベント名を出せない | 2 | 未対応(K-22) |
| 登録アダプタに既定値(予約数 0)を書けない | 1 | 未対応(K-24) |
| 参加費のマイナスを弾いていない(書き忘れ) | 1 | 利用者の記述漏れ。範囲の型(例: `0以上の金額`)があれば防げる(K-25) |
| 何もしなくても安全になる分、仕組みが見えず不安 | 1 | 未対応: 生成した安全対策の一覧を `koto explain` 等で見せる(K-26) |

## 5. 評価の限界
- ペルソナは AI が演じており、人の迷い・学習時間・感情を再現しない。SUS は参考値
- B を書いたのも AI であり、人が書く B より品質が高い可能性がある(特に P1・P3〜P5)
- 課題が KOTONOHA の見本(examples/shop)に近く、写して直すだけで書けた面がある(P2・P4 の指摘)
- 実在の利用者による評価(event_app_trial.md §5)の代わりにはならない
