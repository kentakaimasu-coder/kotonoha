# ペルソナ評価 第 2 回(60 人)の結果

状態: 完了(**AI が演じるペルソナによるシミュレーション。実在の利用者評価ではない**) / 実施: 2026-11-08
ペルソナ: [personas60.md](personas60.md)(N: 慣れていない人・非エンジニア 30 人 / E: いろいろな業種のエンジニア 30 人)
課題: A = 共通課題(イベント受付)を KOTONOHA で、B = 同じ課題を普段の手段で、C = 自分の仕事・生活で欲しいアプリを KOTONOHA で
採点: `tools/eval/probe.mjs`(19 項目)・`tools/eval/grade.sh`。生データ: [round2/](round2/)

## 2. 300% 基準に対する判定
| 観点 | N(主な対象) | E | 300% 以上か |
|---|---|---|---|
| 使いやすさの主観(SUS の比 A/B) | 68.6 / 27.2 = **2.5 倍** | 1.2 倍 | **満たさない**(N は近いが届かない) |
| 書く量(B/A) | 2.8 倍 | 3.4 倍 | N は満たさない、E は満たす |
| 品質 | A は全員満点、B は 28 人が失点 | A は全員満点、B は 22 人が失点 | (比の指標ではない)A が上 |
| 自分のアプリを作れた割合 | 100% | 100% | (B では未測定) |

**結論: 300% は未達(不合格)。** 非エンジニアでは主観評価が 2.5 倍、全員が KOTONOHA を高く評価したが、3 倍には届かない。
エンジニアでは書く量で 3.4 倍だが、主観は 1.2 倍。

注意(結果を良く見せすぎている可能性):
- **B を書いたのも AI**。N の多くは報告で「自分では書けない」「孫・息子が書いた想定」「仕組みが分からない」と記録しており、
  実在の非エンジニアなら B は完成しない可能性が高い。その場合の実際の差はこの表より大きいが、測っていない
- 共通課題 A はひな形「予約受付」とほぼ同じで、多くが書き換えだけで合格した。C(各自のアプリ)は条件が公平に近い
- SUS は AI の回答であり、人の感じ方と同じとは限らない

## 3. 評価中に修正したもの(第 2 回の間に、つまずきを見て順次直した)
役割(ロール)宣言・全件閲覧の許可・本人限定データの分析・集計の公開、日付型、関連データの名前表示、使えない操作のボタンを隠す、
開発用ワンクリックログイン(役割ごと)、koto token、`==` / 列挙値 / 金額の数字 / 識別子の文字列 の書き方の案内、選択型への代入、
詳細画面のフォームの ID 自動入力、他の人の分としての登録(担当者)、宣言した権限の強制(セキュリティ)、koto dev の不具合
(禁止ポート・相対パスの DB・移行できないときの案内・子プロセスの終了)。どれも E2E テスト付きで push 済み。
評価の途中で版が変わったため、前半と後半のペルソナは少し違う版を使っている(各ペルソナの報告の時刻順で追える)。

## 4. 残っている要望(多い順)と、その後の対応(2026-11-08)
| 要望 | 主な声 | 対応 |
|---|---|---|
| 集計に SQL が要る(日本語の文で書きたい) | N の大半。「例を写した」「人の助けが要る」 | ✅ 「注文を品名ごとに集計」など(ADR-0128) |
| API の日時が UTC(…Z)で返る | 多数(画面は日本時間で正しい) | ✅ `+09:00` で返す(ADR-0129) |
| 一覧の絞り込み・並べ替え(今日の分だけ・納期順・未完了だけ) | 多数 | ✅ 「…のうち状態が調理中のものを注文日時順に一覧表示」(ADR-0128) |
| 二重登録の防止(同じ人が同じ回に 2 回申し込める) | 多数 | ✅ 約束「…の組で重複不可」(ADR-0129) |
| 他の人のデータは 404 になり、自分で書いた失敗(「本人以外」)が出ない | 多数(設計どおりだが分かりにくい) | △ 404 のまま、文言を「無いか、ほかの人のものです」に |
| 日付の計算(期限・延滞・〇日後) | 数人 | ✅ `今日()` `日後` `日前` `日数差` |
| 引数付きの分析を画面に出す、他のデータから選ぶ入力(担当者をスタッフ一覧から) | 数人 | △ 選ぶ入力は Web のみ対応。引数付きの分析の画面表示は未対応 |
| フォームのボタン文言(「送信」固定)・入力のヒント・複数行入力 | 数人 | △ 文言(全ターゲット)・複数行(Web)は対応。入力のヒントは未対応 |
| 状態の順番(受付→製作中→出荷済)を強制する書き方 | 数人 | ✅ 約束「…は 受付 → 製作中 → 出荷済 の順」(ADR-0129) |

これらの対応後のペルソナ評価(第 3 回)は未実施。
