## 2. 300% 基準に対する判定
**未達(不合格)。** 主な対象の非エンジニアで主観評価が 2.38 倍(第 2 回 2.52 倍)。追加した機能で C の内容は広がった
(取消・期限切れ・状態の流れ・重複防止を書いたアプリが増えた)が、主観評価は上がらなかった。

主観評価が上がらない理由(報告の記述から数えた。重複あり、60 人中):
| つまずき | N | E |
|---|---|---|
| 会場別の集計を SQL で書くか集計の文で書くか迷う(課題が API の名前と列名を指定しているため SQL が必要) | 30 | 29 |
| 動作確認に curl・トークン・URL エンコードが要る(この人には無理、と書いた人が多い) | 29 | 26 |
| ひな形が無ければ書けない(ひな形頼み) | 26 | 25 |
| 「アダプタ」「厳密」「取引」などの語の意味が分からないまま写した | 25 | 25 |
| データの更新・取消の書き方が分かりにくい | 13 | 17 |
| 画面をブラウザで確かめられない(Cookie のログインが前提) | 16 | 14 |
| 権限名がソースでは日本語(作成・読取)、課題文・トークンでは英語(create・read) | 12 | 15 |

SUS の回答は、ほぼ全員が「4,2,4,3,4,2,3,2,3,3」(65 点)〜「4,2,4,2,4,2,4,2,4,2」(75 点)の範囲に集まった。
AI のペルソナは「ひな形が無ければ書けない」「詳しい人の助けが要る」と書いた上で中間の点を付ける傾向があり、機能の追加では動きにくい。
3 倍(非エンジニアで A の SUS が 82 以上)に届かせるには、**語(アダプタ・厳密・取引)を覚えずに書けること**と、
**ターミナル・curl を使わずに動作を確かめられること**が必要だと読める。

## 3. 評価中に見つけて直したもの(すべてテスト付きで push 済み)
- 「…でないものを…」が解釈できなかった(条件の終わりの「もの」)・「かつ」の前後の空白で的外れなエラー
- 重複不可の判定から取消した行を外せない → `(状態が取消のものを除く)`(部分一意索引)
- 状態の順番に、どこからでも移れる値(取消・中止・見送り)を書けない → `(取消はいつでも)`
- 期限切れの一覧が書けない → `…が今日より前のもの`(今日より後・今日以降・今日まで)
- フォームで「データ名ID」が選ぶ欄にならない場合があった(そのデータの一覧画面が無いとき)
- `koto dev` を止めても画面・backend のサーバーが残る(親がゾンビのとき)
- `koto safety` で本人限定データの集計の公開範囲の表示が途中で切れる・全件閲覧の例外が書かれていない
- `koto check` は合格するのに `koto dev` で TGT001(小数のフィールドなど)→ check でも kotonoha.json の targets の生成可否を確かめる
- 厳密層の条件に「かつ」と書くと構文エラー → `&&` と同じ意味で書ける
- 使っていない権限の警告(SEC002)が「削除してください」とだけ言う → 役割で限定する意図なら残してよいと案内

## 4. 残っている要望(多い順・未対応)
| 要望 | 主な声 |
|---|---|
| 「アダプタ」を書かずにデータを取得・登録したい | 大半(語が分からない・ひな形の写し) |
| ブラウザ以外(curl)を使わずに動作を確かめたい / 画面をトークンで確かめたい | 多数 |
| 一覧の各行にボタンを置く(取り置きを受け取り済みにする等) | 数人 |
| 時間帯の重なりの判定(10 時と 11 時の施術が重なる) | 数人 |
| 番号の自動採番(整理券・受付番号) | 数人 |
| 公開の呼び出し画面(本人限定データの一部の列だけ誰でも見せる) | 数人 |
| 集計の列名・API 名を選びたい(課題の会場別集計を SQL なしで書きたい) | 多数 |
| 回答の変更(一度出した出欠を変える) | 数人 |

## 5. 注意
- **実在の利用者評価ではない。** B を書いたのも AI で、実在の非エンジニアなら B は完成しない可能性が高い(その場合の差はこの表より大きいが、測っていない)
- 共通課題 A はひな形「予約受付」とほぼ同じで、ほとんどの人が書き換えだけで合格した。C(各自のアプリ)の方が実力を表す
- 今回は B をやり直していない(§0)。A と B の比は「第 3 回の A」と「第 2 回の B」の比である
